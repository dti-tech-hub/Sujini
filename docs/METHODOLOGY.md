# Methodology

This document explains how the prototype works and how it was evaluated. It describes the implementation in this repository, not an idealized design. Measured results live in [`EVALUATION.md`](EVALUATION.md) and are generated by `scripts/evaluate.py`.

Data provenance for every bundled dataset and scenario is **`synthetic_demo_data`**. All response effects are **simulated**. No live LLM or threat-intelligence provider was configured for the measured validation run.

## 1. Research questions

The implementation and evaluation target five practical questions:

1. Can deterministic web-security rules separate the generated attack families from benign traffic?
2. Does evidence-driven incident re-triage improve classification over a rule-only baseline?
3. Does the local MITRE ATT&CK mapping reproduce project-defined technique ground truth?
4. Does the approval, allowlist and simulation policy prevent unauthorized or real-world execution?
5. What latency does the prototype exhibit on a local SQLite deployment?

The project does **not** claim production detection accuracy, live-model reasoning quality, real threat-intelligence accuracy, risk calibration or real containment.

## 2. End-to-end pipeline

```text
security events / logs
  -> normalization, sanitization, deduplication
  -> deterministic rules + optional Isolation Forest signal
  -> alerts
  -> incident correlation (source IP / username / time window)
  -> evidence collection and timeline
  -> deterministic investigation triage (LLM optional and advisory)
  -> threat-intelligence enrichment (live, mock, or no-lookup)
  -> MITRE ATT&CK mapping
  -> transparent risk scoring
  -> response planning from policy
  -> durable human approval gate for HIGH/CRITICAL
  -> simulated execution
  -> verification
  -> hash-chained audit
```

The FastAPI service exposes each stage; the Streamlit dashboard is a thin client. The two LangGraph workflows (investigation and response) are separated by the durable approval decision in SQLite.

## 3. Event ingestion and normalization

`src/detection/normalization.py` accepts heterogeneous JSON events, alert-shaped events and Apache/Nginx combined-log lines. It produces a unified event record with:

- UTC timestamp, with an explicit warning when receipt time had to be substituted;
- validated source/destination IPs (invalid values are not promoted);
- sanitized username, method, endpoint, status code, user agent, message and request body;
- bounded field lengths and redaction of secret-like values;
- a SHA-256 deduplication hash over timestamp, source, principal, request and event type;
- prompt-injection flags counted in untrusted text;
- a bounded raw payload plus normalization warnings.

Duplicate events are rejected by the unique `dedup_hash` and audited as `EVENT_DUPLICATE`. They can still attach to an existing correlated incident so that replay does not create a second incident.

## 4. Detection

### 4.1 Signature rules

Rules are declarative in `config/detection_rules.yaml` and are evaluated passively by `src/detection/rules.py`. Payloads are never replayed or executed.

| Rule | Category | Severity | Trigger family |
|---|---|---|---|
| `SQLI-001` | `sql_injection` | HIGH | `UNION SELECT`, tautologies, time-based functions, `information_schema`, `xp_cmdshell` |
| `XSS-001` | `xss` | HIGH | script tags, event-handler attributes, `javascript:` URLs, DOM-sink references |
| `CMDI-001` | `command_injection` | CRITICAL | shell metacharacters followed by OS commands |
| `TRAV-001` | `path_traversal` | HIGH | `../`, encoded traversal, sensitive file targets |
| `RECON-001` | `recon_scanning` | MEDIUM | credential/source-control/admin path probes |
| `UA-001` | `suspicious_user_agent` | MEDIUM | scanner and exploitation tool agents |
| `PROMPT-001` | `prompt_injection_attempt` | MEDIUM | instruction-like text inside log fields |

### 4.2 Behavioral rules

`AlertDetector` evaluates recent event history against configurable thresholds:

| Behavior | Default threshold | Alert category |
|---|---|---|
| Repeated failed logins for one principal/source on authentication endpoints | 5 in 10 minutes | `brute_force` |
| Successful login after at least 3 failures | 10-minute window | `account_compromise` |
| Request rate | 30 requests / minute | `abnormal_traffic` |
| Server-error burst | 10 in 5 minutes | `abnormal_traffic` |
| Access-denial burst (`ACCESS-001`) | 3 in 10 minutes | `unauthorized_access` |
| Explicit denial on a privileged endpoint (`ACCESS-002`) | immediate | `unauthorized_access` |
| Watchlisted source IP | configured list | `malicious_ip` |

Alert `dedup_key` values prevent repeated evaluation from creating duplicate alerts.

### 4.3 Machine-learning anomaly signal

The optional Isolation Forest consumes 14 numeric HTTP features (`src/ml/preprocessing.py`):

```text
status_code, method_post, path_length, query_length,
has_sql_meta, has_traversal, has_cmd_meta,
is_login, failed_login, ua_suspicious,
body_length, hour, response_size, missing_username
```

The runtime model is loaded from `models/anomaly_iforest.joblib`. It contributes an additive `ml_anomaly` alert only when its stored threshold is crossed. Deterministic rules remain authoritative, and a missing or incompatible model artifact is reported as unavailable instead of being silently replaced.

The supervised models (Random Forest, Logistic Regression) are evaluation baselines, not runtime authorities.

## 5. Incident correlation and evidence

`src/detection/incident_manager.py` attaches an alert to an open incident when a recent incident shares the source IP or username inside the correlation window (default 10 minutes). Otherwise it creates a new incident.

The provisional incident state is deterministic:

- severity is the maximum observed rank;
- category follows an explicit priority (command injection > account compromise > SQL injection > XSS > traversal > unauthorized access > brute force > malicious IP > abnormal traffic > reconnaissance > scanner UA > prompt injection > ML anomaly);
- nearby events sharing the correlation key are attached, so the timeline includes non-alerting context;
- `event_count` is refreshed from stored events.

`src/investigation/evidence.py` then persists weighted evidence: one record per alert, recent failed logins, suspicious requests with rule matches, successful logins with prior failures, a correlated failure-then-success sequence, recent access-denied requests, timeline bounds, and prompt-injection text with a containment note. Evidence is deduplicated by type, event and description prefix.

## 6. AI-agent orchestration

`src/agents/orchestrator.py` compiles two LangGraph `StateGraph` workflows.

### Phase 1 — investigation

```text
START -> evidence_collection -> alert_triage -> threat_intelligence
      -> mitre_mapping -> risk_assessment -> response_planning
      -> approval_gate -> END
```

`_run_stage` records an `AgentRun` row (duration, provider, output summary or error) and an audit entry for every stage. Errors are recorded and re-raised; they are not swallowed.

| Stage | Provider label | Output |
|---|---|---|
| Evidence collection | `evidence_rules` | Evidence records, correlation summary, prompt-injection flags |
| Alert triage | `investigation_agent` | Classification, confidence, severity, summary, reasoning, next steps, LLM mode |
| Threat intelligence | `threat_intel` | Indicator verdicts and mode labels |
| MITRE mapping | `mitre_mapper` | Techniques with confidence and confirmed/candidate status |
| Risk assessment | `risk_model` | Score, level, factors and explanation |
| Response planning | `policy_engine` | Allowlisted actions and approval requirement |
| Approval gate | `policy_engine` | `AWAITING_APPROVAL/PENDING` or `APPROVED/NOT_REQUIRED` |

The graph does not hold a process open waiting for a human. The gate writes durable incident and approval state.

### Phase 2 — response

```text
START -> execute -> verify -> END
```

Execution is allowed only when the incident is `APPROVED` or `CONTAINMENT`. Verification runs six checks and marks the incident `VERIFIED` only when all pass.

### State and determinism

The graph state is a serializable typed dictionary containing the incident ID, events, evidence, indicators, threat intelligence, MITRE techniques, severity, risk, confidence, summary, recommended actions, approval status, executed actions, verification result and audit references.

Deterministic triage in `src/investigation/incident_analysis.py` is the authoritative classifier:

- the candidate category comes from alert types by deterministic precedence;
- base confidence comes from a per-category table;
- corroboration adds up to 0.06 for multiple alert types and 0.03 for correlation confidence >= 0.70;
- confidence is clamped to [0.30, 0.97];
- severity is the maximum of the category default and the alert severities.

The reasoning string records the formula inputs (event/alert counts, correlation confidence, failure counts, success-after-failure, alert descriptions and prompt-injection containment).

## 7. LLM abstraction and prompt security

`src/llm/` defines a provider interface with two implementations:

- `deterministic.py` — template investigation text derived from evidence; the default;
- `openai_compatible.py` — optional OpenAI-compatible `/chat/completions` endpoint.

Mode labels distinguish `DEMO_TEMPLATE` from `LIVE_LLM`.

Untrusted log text is never placed in an instruction position:

1. normalization flags instruction-like patterns;
2. evidence records the flagged text with a containment note;
3. the system prompt states that log content is untrusted data and must not be followed;
4. event data is serialized inside an `UNTRUSTED_SECURITY_DATA` envelope, with delimiter occurrence neutralized;
5. output is parsed by a strict Pydantic schema (`extra="forbid"`);
6. classification must be in the allowed set, confidence in [0, 1], list fields are bounded, and destructive-command patterns are rejected;
7. deterministic classification and policy remain authoritative; LLM disagreement is recorded, not obeyed;
8. the LLM has no tool-calling or execution path.

If the LLM times out, returns invalid JSON or fails schema validation, the deterministic provider output is used and the mode is reported accordingly.

## 8. Threat intelligence

`src/threat_intel/service.py` chooses behavior by indicator scope and configuration:

| Situation | Behavior | Mode |
|---|---|---|
| Private / loopback / link-local | No external lookup | `NO_EXTERNAL_LOOKUP` |
| Documentation range (RFC 5737) | Deterministic labelled mock | `DEMO_MOCK` |
| Public indicator, live keys configured | VirusTotal/AbuseIPDB with cache | `LIVE` |
| Public indicator, no keys | Labelled mock fallback | `DEMO_MOCK` |
| Live providers all fail | Mock fallback with provider errors | `DEMO_MOCK_FALLBACK` |
| Invalid IP | Explicit validation error | `INVALID` |
| Disabled | No query | `DISABLED` |

Every record carries `is_mock`, `mode`, provider and details. Conflicting provider verdicts are surfaced (`conflict=true`), not averaged away. Only IP addresses are accepted as indicators, which also bounds SSRF risk.

## 9. MITRE ATT&CK mapping

`src/mitre/mapper.py` derives behaviors from the classification and alert types, then matches the local catalog in `config/mitre_mapping.yaml`.

- each technique has a base confidence, tactics, rationale and behavior triggers;
- corroboration adds 0.02 per evidence item, capped at four items;
- investigation confidence below 0.60 caps technique confidence at 0.70;
- a technique is `confirmed` at >= 0.75 and `candidate` otherwise;
- evidence pointers are attached and deduplicated.

The catalog only contains mappings the project can defend: brute force (`T1110`), valid accounts (`T1078`), public-facing exploitation (`T1190`), command execution (`T1059`/`T1059.004`), JavaScript execution (`T1059.007`, deliberately a candidate because XSS delivery is not proof of execution), vulnerability scanning (`T1595.002`), network denial of service (`T1498`, deliberately a weak candidate) and web shell (`T1505.003`).

Reputation alone, request volume alone and authorization denial alone are not treated as proof of a technique. `malicious_ip`, `abnormal_traffic` and `unauthorized_access` scenarios are excluded from MITRE accuracy.

## 10. Risk scoring

The score is a transparent weighted sum:

```text
score = 100 * sum(weight_i * normalized_factor_i)
```

| Factor | Weight | Normalization |
|---|---:|---|
| Severity | 0.22 | LOW 0.25, MEDIUM 0.50, HIGH 0.75, CRITICAL 1.00 |
| Investigation confidence | 0.13 | clamp(confidence, 0, 1) |
| Asset criticality | 0.13 | highest matching endpoint prefix (`/admin` 1.00 ... `/` 0.40) |
| Threat intelligence | 0.16 | malicious 1.00, suspicious 0.60, unknown/not configured 0.30, clean 0.10, private 0.20 |
| Event volume | 0.08 | `event_count / 20`, capped at 1 |
| Attack impact | 0.23 | category table (account compromise 1.00 ... benign 0.20) |
| Recurrence | 0.05 | prior incidents in 30 days / 5, capped at 1 |

Levels: LOW <= 24, MEDIUM <= 49, HIGH <= 74, CRITICAL >= 75. These thresholds and weights are project parameters in `config/risk_rules.yaml`, not universal cybersecurity standards.

Every assessment stores each factor's raw input, normalized value, weight and contribution, plus a human-readable explanation. There are no ground-truth risk labels, so accuracy and calibration are **NOT MEASURED**.

## 11. Response, approval and verification

`src/response/planner.py` selects actions from `config/response_rules.yaml`:

| Risk | Auto (recorded/notified) | Approval-gated | Advisory |
|---|---|---|---|
| LOW | `NOTIFY_ANALYST` | — | — |
| MEDIUM | `NOTIFY_ANALYST`, `SIMULATE_NOTIFY_ADMIN` | — | `SIMULATE_BLOCK_IP` |
| HIGH | `NOTIFY_ANALYST`, `SIMULATE_NOTIFY_ADMIN` | `SIMULATE_BLOCK_IP`, `SIMULATE_DISABLE_SESSION` | — |
| CRITICAL | `NOTIFY_ANALYST`, `SIMULATE_NOTIFY_ADMIN` | plus `SIMULATE_RESET_CREDENTIAL`, `SIMULATE_QUARANTINE` | — |

Category additions (for example credential reset for account compromise) are approval-gated at HIGH/CRITICAL and advisory at lower levels.

Approval state machine:

```text
NEW -> INVESTIGATING -> AWAITING_APPROVAL (PENDING)
                           -> approve -> APPROVED -> CONTAINMENT -> VERIFIED
                           -> reject  -> REJECTED (audited, no execution)
```

The approver must be an authenticated analyst or admin, and the decision stores approver, timestamp, action, decision and reason. Rejection requires a reason.

The executor independently re-checks:

- `simulation_mode` is true (otherwise `PolicyError`);
- the incident is approved;
- no approval-gated action remains pending;
- every action is in the allowlist and action catalog.

Verification checks action records, execution status, simulation metadata, advisory non-execution, audit presence and unresolved executable actions. Only then is the incident marked `VERIFIED`.

All actions are simulated. The executor records `simulated: true`, `mode: SIMULATION` and an explicit no-effect result. No shell, `subprocess`, `os.system`, `eval`, `exec` or network-mutating call exists in the response path.

## 12. Audit trail

Every ingestion, duplicate, detection, investigation stage, approval, rejection, execution, failure and verification writes an audit row. Rows are chained:

```text
entry_hash = SHA256(previous_hash + canonical_json(entry_without_hash))
```

`AuditService.verify()` recomputes the chain and reports the first mismatch. This detects edits and insertions inside the chain. It does not prevent tail truncation or replacement of the whole database by an actor with write access; there is no external anchor.

## 13. Evaluation design

### 13.1 Event-level ML evaluation

- 4,200 generated HTTP events, 14 numeric features, 8 class labels.
- Stratified 70/30 split: 2,940 train, 1,260 test, seed 42.
- Random Forest (300 trees) and scaled Logistic Regression.
- Isolation Forest fitted on benign training traffic only; its operating threshold is selected on a labelled validation split, never the test split.
- Fixed dataset anchor timestamp so the `hour` feature and event times do not depend on the run date.
- `n_jobs=1` so threshold selection is bit-for-bit reproducible.

Reported metrics: accuracy, macro/weighted/per-class precision-recall-F1, binary attack precision/recall/F1, false-positive rate, ROC-AUC and confusion matrices.

### 13.2 Incident-level scenario benchmark

- 100 scenarios: 10 each for brute force, account compromise, SQL injection, XSS, command injection, path traversal, unauthorized access, malicious IP, abnormal traffic, plus 10 benign.
- Each scenario runs in a **fresh temporary SQLite database** for both arms, preventing cross-scenario correlation.
- ML anomaly detection is disabled in both arms (`enable_ml=False`) so the comparison isolates incident-level re-triage and response policy. ML is evaluated separately.
- Both arms share the same rule stage and the same scenario events.

Baseline: the **earliest rule alert** determines the incident category, with no contextual re-triage. This is a rule-only queue, not a straw man with detection removed.

Agentic arm: runs evidence collection, deterministic re-triage, threat intelligence, MITRE mapping, risk scoring, response planning, the approval gate, simulated execution and verification.

Paired comparison uses McNemar's exact test over discordant classification outcomes.

### 13.3 Metrics

- Detection: TP/FP/TN/FN, precision, recall, F1, accuracy, Wilson 95% interval.
- Classification: accuracy, macro F1, per-class F1.
- Correlation: correct incidents vs expected (one per attack, zero per benign).
- MITRE: micro precision/recall/F1 and exact-set match over eligible categories.
- Response: approval-gate correctness, expected key-action coverage, allowlist compliance, simulation compliance, verification rate, unauthorized executions.
- Audit: chain validity per scenario.
- Latency: per-stage wall-clock mean, median, p95 and max.

Unmeasured quantities are written as **NOT MEASURED**; they are never estimated. Figures are generated only when the underlying data exists.

### 13.4 Baseline and scenario truth

Scenario ground truth (category, MITRE set, key action) is project-defined from scenario construction. It is not independent expert annotation. The account-compromise scenario deliberately includes a SQL injection-shaped admin request so that `T1190` is defensible.

## 14. Reproducibility

- Python and dependency versions, platform and git commit are recorded in the generated report.
- Seed 42 is used for data generation, split, Random Forest, Logistic Regression and Isolation Forest.
- The dataset anchor timestamp is fixed.
- Isolation Forest threshold selection uses `n_jobs=1`.
- The scenario benchmark uses a fresh SQLite database per scenario and per arm.
- Mock threat intelligence is deterministic for documentation-range IPs.
- LLM template output is deterministic.

Wall-clock latency is **not** reproducible and varies with host load. It is reported as a local observation, not an SLA.

## 15. Threats to validity

- **Circularity:** scenarios, ground truth and heuristics share project assumptions. Perfect scores on synthetic data do not imply real-world performance.
- **Small sample:** 100 scenarios and 10 per class give coarse per-class estimates.
- **Weak baseline:** a stateful rule engine with success-after-failure logic would narrow the classification gap.
- **Synthetic ML separability:** the Random Forest's 100% is an artifact of template-generated features.
- **No live LLM:** results describe deterministic templates, not a hosted model.
- **No live threat intelligence:** mock/no-lookup modes only.
- **No independent MITRE ground truth:** the mapper is checked against project-defined sets.
- **No risk labels:** scores are transparent but not calibrated.
- **Simulation only:** verification proves the workflow recorded and marked actions; it does not prove real remediation.

## 16. Non-claims

This project does not claim real-world detection accuracy, production readiness, live-model reasoning quality, live threat-intelligence accuracy, validated MITRE mappings, calibrated risk scores, real containment, throughput/SLA guarantees, or resistance to an attacker with host or database access.
